DEAD! · Gradebook

What happens
when a category
doesn't exist yet?

A weighted gradebook seems like solved territory until you ask one question: what should the grade say in week three of the semester, when the only category with submissions is "Assignments"? This is a case study about catching a silent failure mode and designing the right answer for it.

01 — The setup

A gradebook is a promise. The number it shows is the number that matters.

Every weighted gradebook starts with the same simple model: an instructor sets weights — say 40% Assignments, 40% Tests, 20% Tournaments — and the final grade is the weighted average of category averages. Clean math. Easy to ship. Easy to misunderstand.

Three weeks into a semester, here's the actual state of a real class:

Scenario · Week 3 of FSA-2200
Category Weight Submissions Average
Assignments 40% 4 91%
Tests 40% 0 — no test yet —
Tournaments 20% 0 — none scheduled —

The student has done 4 assignments and aced them. Their actual performance, based on what's been graded so far, is 91%. So what should the gradebook display?

The naive answer is wrong. The intuitive answer is also wrong. Only one answer is right — and it took a deliberate decision to land there.
02 — Two interpretations

The choice was binary, but the reasoning wasn't.

Two implementations were on the table. They produce dramatically different numbers from the same data.

A
Treat empty categories as zero.
Apply the configured weights as-is. If a category has no submissions, its weighted contribution is zero. This is what naive math gives you.
Calculation (91% × 0.40)
+ (0% × 0.40)  // no tests yet
+ (0% × 0.20)  // no tournaments

Final grade 36.4% A 91% performer is told they have an F. The instructor stops trusting the gradebook.
B
Redistribute empty weights proportionally.
If a category has no submissions, its weight is removed from the calculation and the remaining categories' weights are scaled up proportionally to sum to 100%.
Re-weighting Active: Assignments (40)
Inactive: Tests (40), Tournaments (20)
Effective weight: 40 ÷ 40 = 100%

Calculation 91% × 1.00

Final grade 91.0% The grade reflects what the student has actually demonstrated. Trust intact.

Option A is what a junior engineer ships if no one tells them otherwise. The math is "correct" in the sense that it follows the configured weights literally — but the result is meaningless. A teacher looking at a 36.4% in week three has no way to know whether that's the configuration or a real signal.

03 — The harder edge case

Single-category-becomes-100% — and other moments engineering would have asked about.

Specifying "redistribute proportionally" gets you most of the way. But there are sub-cases that need explicit calls. The spec ended up enumerating them so engineering wasn't guessing:

Case 01 · Two of three categories empty

The remaining category becomes 100% of the grade.

CategoryConfiguredHas data?Effective
Assignments40%Yes100%
Tests40%No—
Tournaments20%No—
Effective total100%100%
Case 02 · One of three empty

Remaining two scale up by their original ratio.

CategoryConfiguredHas data?Effective
Assignments50%Yes62.5%
Tests30%Yes37.5%
Tournaments20%No—
Effective total100%100%

Reasoning: with Tournaments inactive, the active pool sums to 50 + 30 = 80. Each active category's effective weight is its configured weight divided by 80: 50/80 = 62.5% and 30/80 = 37.5%. The original 5:3 ratio between Assignments and Tests is preserved.

Case 03 · All categories empty

Display "—" instead of a percentage.

Showing 0% would be wrong (no submissions doesn't mean failure). Showing 100% would be wrong (no demonstrated performance). The spec calls for an em-dash and a tooltip: "No graded submissions yet."

04 — How we got there

The decision wasn't made in a vacuum.

Step 01 · Spotted the bug

Walking through the prototype, the demo grade looked "off"

The mock data had assignments graded but no tests yet. The displayed final grade looked too low. Tracing the calculation revealed the prototype was applying weights literally — the original Option A behavior. It would have shipped that way.

Step 02 · Researched precedents

Looked at how other LMS platforms handle it

Every mainstream gradebook (Canvas, Blackboard, PowerSchool) redistributes by default. Some let instructors toggle the behavior; none ship the literal-weights default. This wasn't an opinion — it was a de facto industry standard the prototype had drifted away from.

Step 03 · Wrote both calculations

Modeled both outcomes on real mock data

Using the prototype's existing mock student "Kate Chen," I worked through Option A and Option B by hand. Option A gave a 36.4%. Option B gave a 91.0%. The contrast made the right call obvious — and gave engineering a worked example to test against.

Step 04 · Specified the edge cases

Wrote out single-category-becomes-100% and all-empty cases

The base behavior is one decision. The corner cases are three more. Each got its own row in the spec doc with input, expected output, and a one-line reasoning note. Pseudocode included for the redistribution itself.

Step 05 · Updated the prototype

Rewrote the calculation; added a walkthrough step explaining it

The prototype's walkthrough drawer — which engineering uses to understand intent — now includes a step describing the redistribution behavior with the worked example baked in. The behavior is documented in three places: code, spec, and the prototype's own narration.

05 — Shipped logic

The calculation, as it lives in the spec.

Pseudocode from the developer handoff document. Engineering implements directly against this:

// Weighted grade with empty-category redistribution
// 1. Filter to active categories (those with submissions)
active = categories.filter(c => c.submissions.length > 0)

// 2. Empty gradebook → display em-dash, no calc
if (active.length === 0) return { display: "—" }

// 3. Compute the redistribution denominator
totalActiveWeight = sum(active.map(c => c.weight))

// 4. Sum the contributions, scaled to 100%
grade = active.reduce((acc, c) => {
  effectiveWeight = c.weight / totalActiveWeight
  return acc + (c.average * effectiveWeight)
}, 0)

Twenty-eight lines in the actual spec, with worked examples, expected outputs for three edge cases, and a sentence explaining why we chose this over Option A. That's how it leaves the design floor.

06 — Outcome

A subtle bug caught before it reached a real classroom.

Had Option A shipped, instructors would have logged in three weeks into a semester, seen failing grades for top students, and either lost trust in the platform or — worse — assumed the grades were correct and acted on them. The redistribution behavior is invisible when it works, which is exactly the bar a gradebook needs to clear.
