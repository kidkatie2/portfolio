01 — The constraint

The constraint.

The developer is remote and speaks English as a second language.

The constraint

Where a sentence could be a diagram, make it a diagram. Where a diagram could be a worked example with real data, make it that. Where a paragraph describes behavior, add pseudocode.

02 — Two ways to write the same spec

The same section, two ways.

Before · ad-hoc style

"The grade switch modal has two paths."

Going from Weighted to Points only needs a confirmation. The other direction needs a confirmation step plus a sliders step where the system suggests weights from the existing point distribution.

After · spec style

§13 Grading System Switch Modal

Two flow diagrams (Weighted→Points: 1 step. Points→Weighted: 2 steps). Annotated screenshots of both modal states. Worked example: 25/35/40 points → 25%/35%/40% sliders. Pseudocode for the auto-balance logic. Expected-state table for both paths.

03 — What's in the doc

Six ingredients in every section.

01

Context SVG

A wide overview diagram showing where the feature lives in the screen.

02

Detail SVG

A close-up annotated diagram — fields, states, copy, dimensions.

03

Worked example

Real mock data through the logic: "Kate Chen has 91% on Assignments and no Test scores. Here's exactly what her gradebook row should display."

04

State table

Inputs → expected outputs for default, empty, error, and loading states. Doubles as test cases.

05

Pseudocode

A function signature plus a few lines of logic.

06

Open questions

Undecided items, listed explicitly.

§13.2 Points → Weighted (two-step path)

When switching from Total Points to Weighted, the system pre-computes suggested weights from the existing point distribution. Show the suggestion on the second step with sliders — instructor can accept or adjust before confirming.

Worked example. Class has Assignments (250 pts), Tests (350 pts), Tournaments (400 pts). Total: 1000.

suggestedWeights = {
  assign: 25,  // 250 / 1000
  test:   35,  // 350 / 1000
  tourn:  40  // 400 / 1000
}

Auto-balance. When any slider moves, others adjust pro-rata to maintain sum = 100. If a slider is locked (👁), it's excluded from the pro-rata. See §13.3 for the locking algorithm.

27 sections · ~120 printed pages · ~140 KB single HTML file.

05 — Principles

Five rules.

01

Feature specs first, reference last.

The first draft opened with design tokens, typography, and component primitives. Reordered: feature specs lead, reference is an appendix.

02

Group by mental model, not chronology.

All grading sections (Calculation, Switch Modal, Assignments Tab) are grouped as §12–14; Assignments was drafted as §16.

03

Build figures from the prototype's actual data.

Every figure uses Kate Chen's grade data, the FSA-2200 mock class, and the real assignment names.

04

Mark shared components.

The grading system picker is built once and used in two flows: Edit Class and Class Create Step 2. Both sections carry a "shared component" note pointing to one source.

05

Leave open questions visible.

§27 API Contract holds placeholders for unfinalized endpoints. Flagged open question: do class-average cells use the same color thresholds as student rows?
